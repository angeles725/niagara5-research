For each delta above, one line of rationale (WHY it matters, what it costs, expected impact):

- **#1** — a "delivered" notification that silently drops its payload is a worse failure mode than a crash, because nothing LOOKS wrong; this wave's recovery (read the block file directly) already worked, so the fix is naming that as the DEFAULT verification step rather than a lucky improvisation, at zero added cost since the block file must exist anyway.
- **#2** — the second retro already named the pattern (LOW priority, PROMPT-LOOP-level); this wave proves a concrete implementation exists and scales cleanly to 15 blocks with zero collisions, so promoting the tool itself (not just re-stating the pattern) saves every future heavy campaign from re-writing the same bookkeeping script.
- **#3** — a fork that quietly does more than it was told is a scope-creep risk that a content-only review will not reliably surface (it looks like "extra diligence," not a defect); explicitly separating "did it touch the right files" from "is the content correct" turns a lucky catch into a repeatable check.
- **#4** — cheap to name, saves the next target-porting session from re-deriving "vendor first, then strip hardcoded paths" as its own discovery; the worked example already proves the technique with a concrete before/after test count.
