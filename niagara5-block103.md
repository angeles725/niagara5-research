**Gap text (verbatim, from `niagara5-block75.md` §75.x):** "**B75-G2** — `PatternFilter`'s full wildcard

**The entire file (`organized/docSource/baja/niagara/util/PatternFilter.java`, 222 lines, pristine
ground truth, read in full this session) settles this exactly.** Its own class javadoc states the intent
plainly: "PatternFileFilter provides simple DOS like pattern file matching where `*` represents zero or
more wildcard characters and `?` represents one wildcard character" `[CERT]` (`:19-21`). The
implementation matches this literally, not just in prose:

```java
private void parse() {
   State cur = start = new State();
   char[] buf = pattern.toCharArray();
   for (int i = 0; i < buf.length; ++i) {
      final char c = buf[i];
      if (c == '*') {
         if (i > 0 && buf[i - 1] == '*') { continue; }         // skip consecutive wildcards
         cur.addTransition(Condition.any(), cur);               // SELF-LOOP: zero-or-more
      } else if (c == '?') {
         cur = cur.addTransition(Condition.any(), new State()); // exactly one, advance state
      } else {
         cur = cur.addTransition(Condition.exact(c), new State()); // exactly this char, advance state
      }
   }
   accept = cur;
}
```
`[CERT]` (`organized/docSource/baja/niagara/util/PatternFilter.java:133-159`, whole method, this session). This is a hand-rolled Thompson-style
NFA builder: a literal character `c` (the `else` branch) creates a NEW state reachable only via
`Condition.exact(c)` (`:193-203`, matches iff `c == test`); `?` creates a NEW state reachable via
`Condition.any()` (`:205-...`, matches ANY char unconditionally) — i.e. exactly one wildcard character,
per the javadoc; `*` does **not** create a new state at all — it adds a **self-transition** on the
CURRENT state (`cur.addTransition(Condition.any(), cur)`), meaning any character can be consumed while
remaining in the same state indefinitely (zero-or-more), and an explicit adjacent-`*`-dedup guard
(`if (i > 0 && buf[i-1] == '*') continue;`) prevents a redundant second self-loop for a run of literal
`**`/`***` in the pattern string. `accept(String string)` (`:102-123`) then simulates this NFA as a
**set** of concurrently-active states (breadth-first, `Array<State> curStates`/`nextStates`), which is
what correctly resolves the ambiguity between "stay in the `*` loop" vs. "this char matches the NEXT
literal/`?` transition instead" for both of `BajadocIndex.lookup()`'s branches [Block 75] §75.2 already
traced. **No character-class (`[abc]`/`[a-z]`) syntax, no escape mechanism (a literal `*` or `?` cannot
be matched), and no path-separator-aware globbing (`**` glob-star directory semantics) exist anywhere in
this file** — `Condition` has exactly two factory methods, `exact(char)` and `any()` (`:189-211`, whole
inner class read, no third variant) — confirming the grammar is precisely the two-token DOS-glob the
javadoc names, nothing richer. **B75-G2 CLOSED**: the full grammar is now `[CERT]`-documented, and per
[Block 75] §75.2's own already-closed argument, this grammar-level detail was never load-bearing for
B59-G2's own closure (which held regardless of the matcher's exact richness) — this section only fills
in the previously-unread remainder of the file.

## 103.4 — B72-G2 CLOSED: `AgentList.getDefault()` is NOT itself a specificity-ranking algorithm — it is a 3-tier `defaultPreference`/list-order lookup, and the actual "most-specific-type-wins" behavior comes entirely from how `NTypeInfo.getAgents()` BUILDS the list (walking the type's `is[]` hierarchy from LEAST to MOST specific, inserting each level at the list HEAD) `[CERT]`

**Gap text (verbatim, from `niagara5-block72.md` §72.x):** "**B72-G2** — `niagara.agent.AgentList.getDefault()`'s
specificity-ranking algorithm (presumably `baja.jar`, not opened this session) — needed to fully certify
that `BCapacityFE` (not `BDefaultSimpleFE`) is what an operator sees BY DEFAULT for a `capacity` slot
absent any `fieldEditor` facet override; this session assumed 'most-specific-type-wins' by Niagara
convention, not by reading the algorithm itself."

**`AgentList` (`organized/docSource/baja/niagara/agent/AgentList.java`, whole 297-line interface read)
documents `getDefault()` trivially: "the agent at index zero"** `[CERT]` (`:28-29`) — the real logic is in
its concrete implementation, `com.tridium.sys.registry.NAgentList` (whole 261-line file read this
session, never previously opened in this corpus):

```java
public AgentInfo getDefault() {
   if (this.list.isEmpty()) { throw ...; }
   AgentInfo secondChoiceAgent = null;
   for (AgentInfo agent : this.list) {
      if (agent instanceof NAgentInfo nAgent) {
         if (nAgent.defaultPreference == 1) { return nAgent; }
         if (secondChoiceAgent == null && nAgent.defaultPreference != 2) { secondChoiceAgent = nAgent; }
      } else if (secondChoiceAgent == null) { secondChoiceAgent = agent; }
   }
   return secondChoiceAgent != null ? secondChoiceAgent : this.list.getFirst();
}
```
`[CERT]` (`organized/baja/vineflower/com/tridium/sys/registry/NAgentList.java:24-45`, whole method, this session). This is a **3-tier lookup, not a
specificity computation**: (1) an agent explicitly flagged `defaultPreference==1` wins outright,
anywhere in the list; (2) otherwise, the FIRST list-order agent not flagged `defaultPreference==2`
(explicitly excluded); (3) otherwise, literally `list.getFirst()`. `defaultPreference` comes from
`@AgentOn(defaultAgent = Preference.{PREFERRED,NORMAL,NOT_PREFERRED})` (`organized/_bin-ext/
niagaraAnnotationProcessors/vineflower/niagara/nre/annotations/AgentOn.java:14-19`), compiled into each
module's `module.xml` and parsed back by the registry `Builder`: `default="true"` → `defaultPreference=1`,
`default="false"` → `defaultPreference=2`, absent → stays `0` (NORMAL) `[CERT]`
(`organized/baja/vineflower/com/tridium/sys/registry/Builder.java:618-623`).

**The actual specificity ranking lives one layer up, in how the list is BUILT — `NTypeInfo.getAgents()`:**

```java
public final AgentList getAgents() {
   NAgentList list = new NAgentList();
   for (int i = this.is.length - 1; i >= 0; i--) {
      NTypeInfo x = this.is[i];
      for (NTypeInfo.NAgentOnInfo xa : x.agents) { list.add(xa.on.getAgentInfo()); }
   }
   return list;
}
```
`[CERT]` (`organized/baja/vineflower/com/tridium/sys/registry/NTypeInfo.java:111-124`, whole method, this
session). `NAgentList.add(AgentInfo)` always inserts at index 0 (`add(AgentInfo info) { this.add(0,
info); }`, `organized/baja/vineflower/com/tridium/sys/registry/NAgentList.java:129-131`), and `this.is[]` is populated by the registry `Builder`'s
`resolveIsTypes()` walking `t.info` → `t.info.superType` → ... starting from the type ITSELF (self is
added FIRST, at `is[0]`, via `Builder.IsMap.add()`'s plain-append/no-reorder semantics) up to the root
`[CERT]` (`organized/baja/vineflower/com/tridium/sys/registry/Builder.java:785-795` `resolveIsTypes(TypeBuild)`, `organized/baja/vineflower/com/tridium/sys/registry/Builder.java:997-1011` `IsMap` — whole
inner class, insertion-order-preserving `ArrayList`). Because `getAgents()`'s loop runs `i` from
`is.length-1` (LEAST specific ancestor) DOWN TO `0` (the type itself, processed LAST), and each `add()`
pushes to the head, **the type's OWN most-specific `@AgentOn` registrations end up added last and
therefore land at the FRONT of the resulting list** — this is the actual mechanism behind "most-specific-
type-wins," proven by construction, not by convention.

**Applied to the original question: neither `BCapacityFE` nor `BDefaultSimpleFE` sets an explicit
`defaultAgent` preference** — `@NiagaraType(agent = @AgentOn(types = "history:Capacity"))` on
`BCapacityFE` and `@NiagaraType(agent = @AgentOn(types = "baja:Simple"))` on `BDefaultSimpleFE` both use
the annotation's default (`NORMAL`, `defaultPreference` stays `0`) `[CERT]`
(`organized/history/vineflower/com/tridium/history/ui/BCapacityFE.java:30`,
`organized/workbench/vineflower/com/tridium/workbench/fieldeditors/BDefaultSimpleFE.java:19`). So
`getDefault()`'s tier-1 check never fires for either, and the winner is decided purely by tier-2 list
order — and since `history:Capacity` (`BCapacity`'s own, most-specific type, registered directly, not via
an ancestor interface) sits closer to `is[0]` than `baja:Simple` (an ancestor interface further toward
the root of `BCapacity`'s `is[]` chain), `BCapacityFE`'s entry is inserted into the head-building loop
LATER than `BDefaultSimpleFE`'s, landing IN FRONT of it. **B72-G2 CLOSED**: `BCapacityFE` beats
`BDefaultSimpleFE` as the unmarked default specifically because of the specificity-ordered `is[]`-walk +
head-insertion construction in `NTypeInfo.getAgents()`, not because `getDefault()` itself ranks by
specificity — confirmed end-to-end by source, replacing [Block 72]'s own "assumed by convention" framing
with a `[CERT]`-level mechanism.
