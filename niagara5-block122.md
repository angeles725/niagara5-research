## 122.4 — Trust boundary and defensive findings `[CERT]` / `[INFER]`

The boundary is a local TCP port on the station host between two processes of the same product: the JVM (station or Workbench) and an elevated .NET process that holds the Milestone credentials and session token. Findings, each with the contract affected and a fix recommendation:

1. **The session key is checked only under TLS.** `AfterReceiveRequest` reads `XPBS_USE_TLS`; only when it equals `"true"` does it require the `SessionId` header and compare it to `XPBS_AUTH_KEY` (`MIPServiceBehavior.cs:40-52`, returns 401 otherwise). With TLS off there is no check at all, so any local process that can reach the port can call all ten operations, including `LoginBasic` with an arbitrary `Uri` (the SDK then connects to that URI with the supplied credentials) `[CERT]`. Java forces `useTls=true` on the first start of a network component and only then makes it editable (`BMilestoneXProtectNetwork.java:170-186`), and the security dashboard raises an alert when it is off (`:284-288`) `[CERT]`. Recommendation: enforce the key regardless of the TLS flag (it is already sent unconditionally, `SOAPMessageHandler.java`), and compare it in constant time (the code uses `String.Equals`).
2. **Fault details are returned to the caller.** `ServiceDebugBehavior.IncludeExceptionDetailInFaults = true` (`Program.cs:114`), and `FindServer` returns null for an unknown `serverId` which then throws inside the operation `[CERT]`. Recommendation: disable in production and map to a fixed fault.
3. **Listener scope is not measured.** The base address names `localhost`, but WCF's documented default host-name comparison for `BasicHttpBinding` is a strong wildcard, which registers the port on all interfaces; nothing in the exe restricts it to loopback and the port probe uses `IPAddress.Loopback` only for the pre-check (`Program.cs:127,139`) `[INFER]`. Confirming it needs an elevated run (`netsh http show urlacl`, `netstat`): B122-G2. A TOCTOU gap between the probe and the WCF bind exists but is local-only.
4. **Credentials cross the boundary in the SOAP body and the default Milestone URI is `http://`.** Java passes username and password as operation arguments (`BXProtectManagementConnection.java:326-335`), the bridge builds a `Basic` credential cache from them (`MIPService.cs:19`), and the login URI defaults to `"http://" + hostName + "/"` (`BXProtectManagementConnection.java:352,416`) `[CERT]`. Whether the SDK upgrades to HTTPS or the server redirects is not measured (B122-G2) `[INFER]`.
5. **Elevation.** The manifest demands `requireAdministrator`; a JVM that is not elevated cannot start it (Windows reports `ERROR_ELEVATION_REQUIRED`, 740, a documented Windows behaviour), and `WebProcessUtil` special-cases only `error=2` (`:136`); other codes surface as "Exception on process exec: …" `[INFER]`.
6. **Telemetry egress is gated by the Milestone server.** `VideoOS.Telemetry` wraps Application Insights (`TelemetryManager.cs`); `MIPTelemetryEnabler` asks the connected management server for its privacy tool option `CollectTelemetryEnabled` (`PrivacySettingWrapper.cs:9`), and the SDK ships production and development ingestion endpoints in the `westeurope` region (`TelemetryKeyProviderBase.cs:7`, key redacted here) `[CERT]`. So the station host can send SDK telemetry to Azure only when the Milestone administrator has enabled it.
7. **TLS validation in the SDK** (sample, not exhaustive): `RecorderStatusService.cs:355-358` accepts a certificate only when `SslPolicyErrors == None`; `SslUtilities.cs:52` uses a reject-all callback for an endpoint probe. Eight callback sites exist (`grep` over the trees); the remaining six were not graded (B122-G5) `[CERT]`.
