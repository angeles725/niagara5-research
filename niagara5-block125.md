## 125.3 — B121-G1 step 2: recompiling the Java-mode text gives 0 of 67 method-wall classes; the 6 class walls give 2 compiling files `[CERT-hw]`

`evidence/b125/grade_sites.py` compiles the top-level Java-mode file of each wall class with `javac --release 25 -g -implicit:none -proc:none` (at most 4 concurrent). Classpath: the shipped classes of the four jars and of the other `_etc-m2` jars, `kotlin-stdlib-2.3.0` (sha256 `887587c91713250ad52fe14ad9166d042c33835049890e9437f355ffc5a195b1`), Gradle 9.2.1 `gradle-api-9.2.1.jar` (sha256 `b5b2c024e2e46b100995c71430437c4ea9194870b4d90b8795e05876987a5c14`, the Gradle version the plugins were built against is not recorded in the jars, so 9.2.1 is an assumption), `groovy-4.0.28.jar` and the Niagara `etc/m2/repository` jars. The recompiled class is compared method by method with the shipped one after the `n5-fidelity.py` normalizer (constant-pool indices dropped, slots canonicalized), then the width allowlist and the `n5_canon.py` canonical comparison (both imported from a frozen copy, sha256 in `evidence/b125/tools-snapshot.sha256`).

- **50 top-level files hold the 73 sites. 48 do not compile; 2 do** (`GruntOptions`, `KarmaConfig`, both class walls). **Method walls recompiled: 0 of 67.** First javac error per non-compiling file: `illegal start of expression` 26 (a `<unrepresentable>` placeholder where the plugin failed to name a Kotlin lambda class), `is not abstract and does not override abstract method execute(Object)` 13 (an anonymous class printed without the body of the `Action` it implements), `constructor Companion ... cannot be applied to given types` 5, one `cannot assign a value to final variable`, one generics syntax error, 2 unresolved-package errors (`org.apache.commons.configuration2`, `org.bouncycastle.asn1`, not on the classpath used here; the null-patched probe below shows 18 files that reference `org.bouncycastle.*` or `commons-configuration2`).
- **Probe with the placeholders replaced by `null`** (`B125_PATCH_UNREP=1`, `java-grades-patched.tsv`): still 48 of 50 fail. The syntax errors disappear and the next layer shows, counting files whose error set contains each kind: anonymous class not implementing `Action` 42, undeclared symbols (`$default` helpers, `$tmp0`, lambda variables the text never declares) 26, other 22, incompatible types 20, missing packages 18 (all `org.bouncycastle.*` and `org.apache.commons.configuration2`, none of them on the classpath used here), `Companion` constructor mismatch 14, references to Kotlin-generated `$inlined$sam$i$…` class names that javac cannot access 13, missing enclosing instance 5, remaining syntax errors 4. So the placeholders hide, not cause, the failure; the Java-mode text is unrepresentative at every lambda, not only at the marked ones.
- **Grades for the 75 rows:** no-compile 73, and for the two compiling class walls the per-method grades of §125.4. No method wall reaches `exact`, `equivalent` or `canonical` (`evidence/b125/java-grades.tsv`, `wall-sites.tsv` column `java_grade`).

Recompiling Java-mode Kotlin output recreates Kotlin-compiled bytecode only approximately in any case (`Intrinsics` calls, `$default` synthetic methods, `@Metadata`); the measurement shows that for these classes the text does not even reach that stage. `[INFER]` for the cause statement "Vineflower Java mode cannot express Kotlin lambda classes": the errors say so at 39 of 48 files, the remaining files fail on companion constructors, final-variable assignment and classpath.

## 125.5 — What Java mode does carry at the wall methods: 251 of 255 string constants and 418 of 434 invoked names present in 56 located bodies (coverage proxy, not a grade) `[CERT-hw]`

`evidence/b125/java_body_metrics.py` locates each wall method's declaration in the Java-mode file, brace-matches the body, and checks which `ldc` string constants and invoked method names of the shipped method (`javap -c`) occur in that text. **56 of 67 method walls located** (the 11 unlocated are 8 top-level facade functions in `NiagaraNativePluginKt`, `ConfigurationExtensionsKt` and `CopySpecExtensionsKt` plus `GruntPlugin.configureTask`, `NiagaraModulePlugin.createModuleManifestElementsConfiguration` and `DefaultNiagaraNativeExtension.registerTaskForNativePlatform`, whose printed signature the matcher does not parse). In the 56: **31 bodies have no `<unrepresentable>` placeholder, 25 have at least one** (49 placeholders in total) and 191 inline-expansion marker names (`$i$f$…`, `$i$a$…`) appear. Constants present 251 of 255 (98.4%), invoked names 418 of 434 (96.3%); for the 31 clean bodies 87 of 91 and 179 of 194. For the six class walls the whole file was checked: constants 103 of 103, invoked names 248 of 258.

Reading: Java mode is a good reading aid for what a wall method touches (names, literals, call targets), as [Block 121] §121.9 rule 2 says, but it is not a compilable source and the presence of a name says nothing about order or control flow. `[INFER]` for anything beyond presence.

## 125.6 — The plugin's own `// Bytecode:` listing is complete for 65 of 67 wall methods `[CERT-hw]`

The durable Kotlin-plugin trees (`organized/_etc-m2/<jar>/vineflower2/`, built with `dump_bytecode_on_error`) keep an instruction listing inside each "Couldn't be decompiled" method. `evidence/b125/plugin_bytecode_dump.py` counts it against the shipped method's `javap -c` instruction count: **65 of 67 equal** (4,315 listed instructions against 4,383 shipped over all 67). The two exceptions: `DefaultNiagaraNativeExtension.registerTaskForNativePlatform` (121 listed, 123 shipped) and `SigningProfileProperties.getProperty` (19 listed against 85, the wall is one of two overloads and the pairing picked the other; child gap B125-G4). This makes the plugin tree itself a partial representation at the wall: a complete instruction stream without offsets resolved to names. It is not more readable than `javap -c`, which also names the operands.

## 125.7 — Why the Kotlin plugin fails: one exception for all 67 method walls, always at a synthetic class that has no metadata `[CERT-hw]`

Tally per wall id (`wall-sites.tsv`, `plugin_failure_kind`):

| Plugin failure | Sites | Where |
|---|---|---|
| `IllegalStateException: Anonymous class does not have Class Kotlin metadata` | **67** (all method walls) | `KotlinWriter.writeClassDefinition` reached from `KNewExprent.toJava` |
| `ArrayIndexOutOfBoundsException: Index 0 out of bounds for length 0` | 4 (class walls `GruntOptions`, `KarmaConfig`, `SignedTar`, `SignedZip`) | `KotlinWriter.writeMethod` |
| `NullPointerException: ... "n.simpleName" is null` | 2 (class walls `SigningProfileFactory`, `LocalSigningProfile`) | `KotlinWriter.lambda$writeClass$0` |

For the 67 method walls the **trigger** is read from the shipped method's bytecode (`javap -c -p -l -s`; non-exclusive labels): every one of the 67 instantiates a synthetic Kotlin class (67 of 67; these are the `k=3` classes of [Block 121] §121.5 that carry no `d1` payload, so the plugin has nothing to print), of which 22 also contain lambdas compiled to `invokedynamic` (bytecode `LambdaMetafactory` bootstrap), 7 the `$sam$i$org_gradle_api_Action$0` wrapper, 5 an `$inlined$` object from an inline-function expansion (`configure`, `the`) and 5 call a `…$lambda$N` body method. Co-occurring constructs in the same methods: `$i$a$` inline-body markers in 31, `$i$f$` inline-function expansion markers in 17, an `object` `INSTANCE` load in 15, a `$default` call in 9, `CloseableKt.closeFinally` calls in 2, a `$WhenMappings` table in 1. **Not causes:** coroutines (0 of the 51 wall-class `javap` dumps mention `kotlin/coroutines`, `COROUTINE_SUSPENDED` or `Continuation`, consistent with [Block 121] §121.4), and `when` expressions (1 site, and it fails for the same anonymous-class reason). Inline functions are involved only as the origin of the anonymous class the plugin cannot write, so "inline functions" and "lambdas" are one failure class here, not two. The 6 class walls are a second, separate defect (metadata for a member with no name or no parameters) and are not lambda-related.

## 125.8 — Best representation per site: `javap -c` for all 75 rows, Java-mode text as the readable companion for 36 `[CERT-hw]`

Rule applied by `build_index.py`: a site's best representation is the Java-mode text only when its class recompiles and the method grades `exact`, `equivalent` or `canonical`; otherwise the `javap -c -p -l -s` dump, which is the shipped bytecode. Result: **`javap` 75, Java-mode 0**. The readable companion (Java-mode file, for a located method with no placeholders, or a whole class wall file) is set for 36 rows, `-` for the other 39. The `kotlin.Metadata` declaration listing is recorded for every row and answers "what is declared" (nullability, `lateinit`, defaults, extension receiver), never the body ([Block 121] §121.5). Claim rule for future writers: at a wall site cite `javap -c` for behaviour, the metadata listing for declarations, the Java-mode file only as "the text prints X" and never as source identity; a `<unrepresentable>`, `$this$…` or `$i$…` name is not evidence.

## 125.10 — Typed walls and limits

- **Java-mode recompile wall** (`blocked-on-tool`): Vineflower 1.12.0 Java mode prints `<unrepresentable>` and anonymous classes that do not implement their `Action`; 0 of 67 method-wall classes compile even with the placeholders nulled (§125.3). Faithful Java source for these methods needs a tool that resolves each placeholder to its shipped synthetic class (child gap B125-G1).
- **Classpath limit** (`blocked-on-source`, 18 files in the null-patched probe, 2 as first error): the signing classes (`JarSignerSigningProfile`, `LocalSigningProfile` and their users) import `org.apache.commons.configuration2` and `org.bouncycastle.asn1`, which are on none of the classpaths used here (the four jars' sibling jars, `_v2-libcache`, Gradle 9.2.1 `lib`, `etc/m2/repository`); they are Gradle-resolved dependencies of the plugin, not files of the install tree checked here. `LocalSigningProfile` also fails the `NullPointerException` class wall, so the classpath is not its only blocker.
- **Gradle API version** is assumed (9.2.1, the newest wrapper on this machine); the jars do not record the build version. A different version could change symbol errors, not the placeholder and anonymous-class errors.
- Method matching (§125.2) is by name, arity and printed parameter types; 2 walls stay ambiguous between overloads and 11 method bodies are not located in the Java-mode text (§125.5).
- The coverage proxy of §125.5 measures presence, not equality; it is `[INFER]`-level evidence of readability and not a fidelity grade.
